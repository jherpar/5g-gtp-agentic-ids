# Appendix: BS1_each_attack_csv Ground Truth Validation

**Status: standalone validation study, appendix material.** This document
does not modify, supersede, or change any conclusion, label, model,
threshold, agent, or output from Phases 4–8 (all frozen — see
`experiment_plan.md` for the primary, reported results). It is an
independent, read-only cross-check of this project's own ground-truth
labeling methodology (Phase 4/4C) against a data source that was never
used to build that methodology in the first place.

Generated by `scripts/analyze_bs1_each_attack_csv_validation.py`. Full
per-attack-type tables (confusion matrices, tier-by-tier confirmation
rates for all 9 types individually) are in
`outputs/reports/bs1_each_attack_csv_validation/report.md` (gitignored,
regenerate with the script above); this document summarizes the
methodology and headline findings.

## Why this study exists

`data/raw/BS1_each_attack_csv/BS1_each_attack_csv/*.csv` is a
previously-unused per-attack-type flow export from the dataset authors
(Argus-derived, one row per biflow). Unlike `Combined.csv`/`Encoded.csv`
(which have no IP/port columns at all — a known limitation noted from the
start of this project), these files retain real `SrcAddr`/`DstAddr` IP
addresses alongside a per-flow `Label`/`Attack Type`/`Attack Tool`. That
makes them usable as an **independent ground-truth reference** for our
own Level 1/2/3 labeling (`preprocessing/labeling.py`), which was built
entirely from the descriptor paper's published schedule and our own
packet-level pattern checks — never from this file.

## Objective 1–2: structure

9 attack-type files + `SSH1.csv` (pure benign), 108 columns each, one row
per Argus biflow (`StartTime`/`LastTime` format `MM:SS.s`, no date/hour —
ordering is only reliable within a single-hour capture and was **not**
used here; see Methodology). Identifiers: `SrcAddr`, `DstAddr`, `Sport`,
`Dport`, `Proto`. Ground truth: `Label` (Benign/Malicious), `Attack Type`,
`Attack Tool`.

| Attack type | rows | malicious rows |
|---|---|---|
| ICMPflood | 18,279 | 613 |
| UDPflood | 467,717 | 175,811 |
| SYNflood | 44,636 | 4,792 |
| Goldeneye | 93,803 | 76,121 |
| Slowloris | 31,015 | 6,207 |
| Torshammer | 38,120 | 29,885 |
| SYNScan | 11,450 | 10,019 |
| TCPConnect | 11,645 | 10,022 |
| UDPScan | 10,043 | 7,887 |

Naming differs from our filename tokens for two types (`TCPConnect` →
`TCPConnectScan`, `Goldeneye` → `HTTPFlood`), and the author's own export
**collapses Slowloris and Torshammer into one `SlowrateDoS` category** —
an independent confirmation that these two belong together, consistent
with `preprocessing/labeling.py`'s own `_PATTERN_CATEGORY` grouping them
as `"slowrate"`.

One data-quality quirk: `TCPConnect1.csv`'s `Attack Type` column header
has trailing whitespace (stripped on load).

## Methodology: matching without touching the frozen labels

For every one of the 9 attack types, the malicious rows have **exactly
one** source IP and **exactly one** destination IP — always
`10.41.150.68` as the destination. That value is derived independently
here (mode of `SrcAddr`/`DstAddr` among `Label==Malicious` rows, computed
fresh from this CSV) and **matches `configs/attack_schedule.yaml`'s
`victim_ip` exactly, for all 9 types** — an external confirmation of a
value this project already committed to, from a source that played no
part in choosing it.

| Attack type | attacker_ip (author) | victim_ip (author) |
|---|---|---|
| ICMPflood | 10.155.15.9 | 10.41.150.68 |
| UDPflood | 10.155.15.4 | 10.41.150.68 |
| SYNflood | 10.155.15.4 | 10.41.150.68 |
| Goldeneye | 10.155.15.3 | 10.41.150.68 |
| Slowloris | 10.155.15.0 | 10.41.150.68 |
| Torshammer | 10.155.15.4 | 10.41.150.68 |
| SYNScan | 10.155.15.1 | 10.41.150.68 |
| TCPConnect | 10.155.15.1 | 10.41.150.68 |
| UDPScan | 10.155.15.9 | 10.41.150.68 |

(The attacker IP varies per type, unlike `attack_schedule.yaml`'s single
`attacker_ip_hints.BS1` value — that field was documented from the start
as a hint never used for gating, only victim-IP matching is, so this
doesn't contradict anything load-bearing.)

"Author confirms attack" for one of our own TEID-instances/sessions is
defined as: does **any packet** in that instance touch this exact
(attacker_ip, victim_ip) pair, in either direction? This sidesteps the
CSV's ambiguous timestamp format entirely — the comparison is
identifier-based, not time-based — and reuses only already-computed,
frozen fields (`preprocessing/labeling.py`'s output via
`scripts.validate_labeling.process_file`, read-only).

## Objectives 3–5: agreement, precision, recall

**Overall (pooled across all 9 attack types):**

| Granularity | Predictor | agreement | precision | recall |
|---|---|---|---|---|
| TEID (n=475) | Schedule label (`is_attack`) | 0.571 | 0.137 | 0.941 |
| TEID (n=475) | **HIGH+MEDIUM subset** | **0.992** | **0.941** | 0.941 |
| Session (n=20,864) | Schedule label (`is_attack`) | 0.663 | 0.124 | 0.917 |
| Session (n=20,864) | **HIGH+MEDIUM subset** | **0.996** | **0.996** | 0.917 |

**Confidence-tier confirmation rate** (of our own attack-labeled
instances at each tier, what fraction does the author's independent
dataset also mark as attack traffic for that exact IP pair):

| Tier | TEID: n / confirmed / % | Session: n / confirmed / % |
|---|---|---|
| HIGH | 24 / 23 / **95.8%** | 135 / 135 / **100.0%** |
| MEDIUM | 10 / 9 / **90.0%** | 856 / 852 / **99.5%** |
| LOW | 200 / 0 / **0.0%** | 6,944 / 0 / **0.0%** |

## Interpretation

This is a strong, independent external validation of the Phase 4/4C
labeling methodology, from a data source never used to build it:

- **The raw schedule label alone is a weak predictor** (precision
  0.124–0.137) — expected and already known internally (this project's
  own ~14.5% TEID / ~12.5% session HIGH+MEDIUM corroboration rate,
  `experiment_plan.md`), and now independently corroborated by a
  completely different ground-truth source landing in the same range.
- **The HIGH+MEDIUM confidence subset is an excellent predictor**:
  agreement 0.992–0.996, precision 0.941–0.996. The confidence-tier
  system built in Phase 4C is doing exactly what it was designed to do.
- **LOW-confidence "attacks" are confirmed to be background traffic, not
  attacks, at both granularities and across all 9 types (0.0% author-
  confirmed, n=200 TEID / n=6,944 session)** — direct, independent
  support for this project's decision (`experiment_plan.md`) to treat
  LOW confidence as unreliable for training and exclude it from the
  trusted (view B) label set, rather than an untested assumption.
- **HIGH confidence is confirmed 95.8–100.0% of the time**, MEDIUM
  90.0–99.5% — both tiers are, per this independent check, close to
  ground-truth-correct.

## Caveats

- **Matching granularity is coarse (IP-pair, not flow-level)**: an
  instance is marked "author-confirms" if *any* packet touches the exact
  attacker↔victim pair, not matched flow-by-flow via ports or timestamps
  (the CSV's `StartTime`/`LastTime` format doesn't support reliable
  cross-referencing without a date/hour, as noted above). Given the
  results above (near-perfect agreement for HIGH+MEDIUM), this
  coarseness does not appear to be masking a real disagreement, but a
  flow-level match was not attempted.
- **BS1 only**, consistent with the rest of this project's scope
  (`experiment_plan.md`'s Limitations).
- **This does not re-validate Level 3 (pattern) evidence specifically**
  — the comparison is against `is_attack`/`label_confidence` as a whole,
  not against which of Level 2/Level 3 individually drove a given
  instance's tier.
- This is a validation study only. No model was retrained, no threshold
  or label was changed, and no Phase 4–8 conclusion is altered by these
  findings — they corroborate the existing methodology rather than
  replacing any part of it.
